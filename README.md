# Требования к запуску

1. Linux (можно внутри виртуальной машины или WSL/docker)
2. python3
3. scapy (2.7.0 или новее)
4. make (можно поменять на cmake/bazel или аналоги, если больше нравится)
5. gcc (можно поменять на clang, если больше нравится)

# Отношение к ИИ

При выполнении задания **запрещено использовать ИИ для генерации кода**. Код должен написать полностью человек.

Можно использовать ИИ только для того, чтобы получать необходимую информацию о тунелях, как работают сокеты, как работают сети,
можно от ИИ получать идеи о том как лучше разбить на классы или какие есть паттерны проектировани.

Просить объяснить код тоже можно, **но генерировать код нельзя** т.к. цель работы заключается в оттачивании навыков C++ и углублении понимания телекоммуникационных технологий.

# Описание скриптов

- `sudo bash ./cleanup_test_artifacts.sh` - Удаляет созданные во время тестирования логи и pcap файлы
- `sudo bash ./compile_and_run_simulators.sh` - Вызывает компиляцию (make) проекта и запускает проект с симулятором UE (fake_ue.py) и симулятором DN (ping)
- `sudo bash ./run_fake_upf.sh` - Запускается fake_upf.py (упрощенный пример на питоне GTP-U тунелирования, по нему видно, что должен делать UPF), fake_ue.py и ping (симулятор общения с DN).

Вспомогательные скрипты:

- `sudo bash ./net/enable_net.sh` - Настроить сети для тестирования программы
- `sudo bash ./net/disable_net.sh` - Выключить сети для тестирования программы
- `cd tests && sudo bash test_network.sh` - Скрипт для тестирования правильности настроек сети (`./net/enable_net.sh` и `./net/disable_net.sh`)

## Интерфейсы и пространства имён (изоляция программ)

Скрипт настраивает 3 пространства имён:
- `DN_ns`
- `gNB_ns`
- `UPF_ns`

Каждое пространство имён (namespace) обладает своими интерфейсами и является чем-то наподобие "песочницы". Т.е. только при запуске программы внутри её
пространства имён будут видны её интерфейсы.

Скрипт настраивает интерфейсы для UPF, gNB+UE (`./fakes/fake_ue.py`) и DN:
- `dn_veth` - Интерфейс со стороны DN до UPF (доступен только внутри пространства имён `DN_ns`)
- `gnb_veth` - Интерфейс со стороны gNB (+UE) до UPF (доступен только внутри пространства имён `gNB_ns`)
- `upf_cn_veth` - Интерфейс со стороны UPF до DN  (доступен только внутри пространства имён `UPF_ns`)
- `upf_an_veth` - Интерфейс со стороны UPF до gNB (+UE) (доступен только внутри пространства имён `UPF_ns`)

Эти интерфейсы имитируют подключения компонент следующим образом:

```
+--------------+         +-------------------------------+         +---------------+
| DN   [dn_veth]<------->[upf_cn_veth]  UPF  [upf_an_veth]<------->[gnb_veth] gNB  |
+--------------+         +-------------------------------+         +---------------+
```

Чтобы запустить программу внутри какого-то пространства имён (для доступа к её интерфейсам) можно воспользоваться командой:

```bash
ip netns exec <namespace> <команда>
```

Пример запуска симулятора gNB и UE внутри `gNB_ns` неймспейса:
```bash
ip netns exec gNB_ns python3 fakes/fake_ue.py
```

Пример симуляции трафика из DN (для того, чтобы DN пустил трафик в сторону UPF надо из `DN_ns` обратиться к `dn_veth` интерфейсу) к `fakes/fake_ue.py`:
```bash
ip netns exec DN_ns ping 192.168.7.1 -I dn_veth
```

## Сети между UPF, DN, gNB

Внутри неймспейсов сконфигурированы следующие подсети:
- `192.168.9.0/24` - AN (access network) подсеть (т.е. сеть между UPF и gNB)
- `192.168.5.0/24` - DN подсеть (т.е. сеть между UPF и DN)
- `192.168.7.0/24` - подсеть для UE

Чтобы DN мог достучаться до UE через тунель, настроен маршрут для перенаправления трафика с адресами из сети `192.168.7.0/24` в интерфейс `dn_veth`.

Т.е. трафик для UE (адреса сети: `192.168.7.0/24`) будет маршрутироваться в интерфейс `dn_veth`. Поскольку `dn_veth` связан с `upf_cn_veth`, то он попадёт в интерфейс `upf_cn_veth`.

Адреса компонент:
- gNB имеет IP адрес `192.168.9.2` на интерфейсе `gnb_veth`
- UPF имеет UP адрес `192.168.9.1` на интерфейсе `upf_an_veth` (в сторону gNB)
- DN имеет IP адрес `192.168.5.1` на интерфейсе `dn_veth` (в сторону UPF)
- Для интерфейса `upf_cn_veth` адрес UPF-а в сети DN `192.168.5.2`.

Подытожим схемой:

```
+------------------+         +-------------------------------+         +-------------------+
| DN   [dn_veth    ]<------->[upf_cn_veth]  UPF  [upf_an_veth]<------->[gnb_veth   ]  gNB  |
|      [192.168.5.1]         [192.168.5.2]       [192.168.9.1]         [192.168.9.2]       |
+------------------+         +-------------------------------+         +-------------------+
```

# Отладка

Проект создает файлы для каждого компонента:
- <компонент>.log - файл содержащий логи компонента, для упрощения выведенные в stdout. Открываются в любом текстовом редакторе;
- <компонент>.pcap - содержащий перехваченные пакеты при помощи утилиты `tcpdump`. Можно открыть в программе [Wireshark](https://www.wireshark.org/download.html).

Самостоятельно можно подправить Makefile для включения address sanitizer. См. [-fsanitize=address](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html#index-fsanitize_003daddress). Он может быть очень полезен для того, чтобы находить ошибки работы с памятью. Или использовать [valgrind](https://valgrind.org/info/about.html).

# Задача

Нужно сделать упрощенное тунелирование GTP-U на языке C++.

Чтобы её решить нужно:
1. Открыть RAW сокет на интерфейсе `upf_cn_veth` в UPF, поймать весь трафик для UE (`192.168.7.0/24`).

    NOTE:

    Рекомендуемые параметры raw сокета: AF_PACKET, SOCK_RAW, htons(ETH_P_ALL). Так же надо его привязать при помощи bind к интерфейсу upf_cn_veth.

    По желанию можно вместо RAW сокета использовать более сложные технологии, например, VPP/DPDK.

2. Провалидировать трафик (такая UE существует, входящий некорректный пакет не должен вызывать отказ в обслуживании UPF или падения программы)
3. Ответить на ARP запросы к DN (чтобы DN знал, что эти IP адреса существующие). UPF должен ответить IP UE и своим MAC адресом.
4. Переслать трафик к UE трафик через GTP-U тунель (через `upf_an_veth` интерфейс в сторону gNB+UE симулятора).
5. UPF должен принять трафик от UE по GTP-U тунели, провалидировать и передать в DN.

    NOTE:

    Некорректные пакеты не должны вызывать отказ в обслуживании или падения программы, а должны быть отброшены.

    UE может притвориться другим IP, нужно отбрасывать такие пакеты.

6. Все взаимодействия с сетью должны быть асинхронными. Для этого можно использовать любой подходящий фреймворк (например, `boost::asio`, `seastar`, ...).

   Примечание: Асинхронные взаимодействия с сетью не означают использование многопоточности. Однопоточный код может быть асинхронным, если использовать
   
   такие технологии как epoll, iouring или неблокирующие сокеты. Т.е. нужно использовать любую библиотеку на базе этих технологий.

7. **[Дополнительное задание]** Можно использовать broadcast address в качестве MAC адреса получателя при отправке пакетов от UE в DN.

    Но, в качестве оптимизации, можно реализовать более честный алгоритм получения MAC адреса получателя (DN). При помощи ARP протокола узнать MAC адрес

    DN (`192.168.5.1`) и добавить в ARP таблицу. Запись в ARP таблице (пара IP+MAC next hop маршрутизатора - в нашем случае DN `192.168.5.1`) должна

    быть валидной пока пакеты с этим MAC адресом приходят. Запись должна инвалидироваться, если 1 минуту не было пакетов от этого MAC адреса.

    После инвалидации записи в ARP таблице надо снова через протокол ARP узнать MAC адрес `192.168.5.1`.

В качестве упрощения (чтобы не делать PDU Session Establishment) предлагается зашить в програму следующие параметры тунелей GTP-U:
- UE1: 192.168.7.1 TEID_dl=2 TEID_ul=3
- UE2: 192.168.7.2 TEID_dl=4 TEID_ul=5
- UE3: 192.168.7.3 TEID_dl=6 TEID_ul=7
- UE4: 192.168.7.4 TEID_dl=8 TEID_ul=9

Где TEID_dl - TEID выделенный для отправки нисходящего (Downlink) трафика ("слушается" gNB, т.е. `fakes/fake_ue.py`).
А TEID_ul - TEID выделенный для восходящего (Uplink) трафика (его "слушает" UPF и по этому TEID отправляет в DN)

То есть:
- TEID_dl использует UPF для отправки нисходящего (Downlink) трафика к gNB
- TEID_ul использует gNB для отправки восходящего (Uplink) трафика к UPF

Весь код на C++ для решения задачи должен располагаться в папке `src` или подпапках внутри `src/`.

В файле `src/tun.cpp` реализована функция main программы.

Код должен быть разбит на модули.

Протокол GTP-U описан в [TS 29.281](./ts_129281v170500p.pdf)
